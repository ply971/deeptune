## Decisions

- **Cacheable sampling.** Everything at evaluation time; in training only `uniform` over the whole clip with no
  `--clip_duration_sec` and no `--video_augment`. Other training clips bypass the cache with one logged warning.
  A test draws from the real sampler for every combination and checks the rule against what it finds. Bypassed
  clips still get the same resize, so train and val match.
- **Cached frames are resized (default 256 short side), so a cached run is not pixel-identical to an uncached
  one.** Frames are resized twice (cache, then model). `--frame_cache_size 0` is exactly identical (tested). The
  setting is recorded, so inference matches the trained pipeline.
- **Key** is the source fingerprint, sampling spec, exact indices, size, resolved backend and a format version.
  The fingerprint comes from I-001: for files it is path + size + mtime, not a content hash, so reads stay cheap.
  A file rewritten with identical size and mtime is not detected, and a moved dataset misses the cache.
- **Crash safety.** Unique `.part` file, fsync, `os.replace`; reads check dtype, shape and exact file size. There
  is no content checksum, so bit rot inside a complete file is not detected.
- **Snippet formula.** `N = min(1 + ceil(max(F-S,0)/R), ceil(F/R))`. The first term is the plan's formula. The
  `min` is needed only for `R > S`, where the plan's formula would start a snippet after the last frame.
- **float16.** NaN, inf, overflow and all-values-vanish fail that video, are listed in `failed.json`, and make the
  CLI exit 1; nothing is stored. I chose failing over clipping because a clipped feature is silently wrong. There
  is no float32 fallback flag.
- **Token grids are capped, never upsampled.** `r3d_18` on 16 frames gives at most `2x7x7`, so `8x4x4` is stored
  as `2x4x4`, and the sidecar records it. This matters for P-102: the 8-temporal-token grid only exists for frame
  backbones and transformers. Streams with different grids cannot be concatenated (clear error).
- **Motion stream.** Vectors are rotated to display orientation, rescaled to input pixels per frame, clipped to
  +-20 and divided by 20. Padded frames are zero. Motion uses the frame count rgb actually decoded, so both streams
  have the same N. dx, dy and their magnitude go through the RGB filters, not a repeated mean filter. The weights were
  not trained on motion, and the sidecar says so (`motion_weights_trained_on_motion: false`). With the cached pretrained
  weights, uniform fields do differ: relative feature distance right vs down is 0.78 (r3d_18) and 0.40 (resnet18), and
  (0.5,-0.5) vs still is 1.23 and 0.54. That shows sensitivity to direction, not that the features are useful.
- **Ids** depend only on the row (`video_id` column, else stem + hash of the path), so a split finds the features
  of the full manifest.
- **`--feature_weights none`** uses a fixed seed, so random-weight extraction is reproducible for tests. Sidecars
  record `weights: null` and a warning is logged.
- **ViT and MViT vectors** are the mean of patch tokens, not the class token (documented in the module).

Decisions:

- **The motion check runs after `load` in `load_snippet_features`.** A missing file or impossible stream therefore still reports
  itself first. `FeatureStore.load` has no version check, because it reads `features.json` and runs per sample;
  `CachedFeatureDataset` checks once when built.
- **A moved dataset is refused.** A row's path must be the extracted path, so manifests with new paths need a new extraction
  or an id-only manifest. The fingerprint already contains the resolved path, so a move invalidated the entries anyway.
- **A path row against features from bytes is refused even when it is the same clip.** The sidecar keeps only the bytes' sha1,
  and a file's fingerprint is path + size + mtime, so the two cannot be compared without reading the file. An id-only row is
  the way to use such features.
- **Cost of hashing bytes rows** (CPU, best of 5, 20 clips, 0.106 MB in all, one measurement session). DataFrame: 5.2 ms to
  build with the check, 5.2 ms without. Parquet file: 9.8 ms with, 8.8 ms without. This example is too small to show the hash
  beside the sidecar reads. Throughput through the memory-mapped store was 741 MB/s (64 rows of 2 MB, file just written, so
  in the page cache). At that rate 100 GB of clips would take about 2.5 minutes per build, which is an extrapolation; a cold
  disk will be slower and was not measured.
- **Bytes from a parquet file are not already in memory.** They sit in a memory-mapped store, so the check reads the whole clip
  column from disk once per build, one clip at a time, which also fills the page cache. Peak memory stays one clip. DataFrames
  are in memory already. A row without a `video_id` is hashed twice, because its id is also derived from the hash.
- A later run may still give an id another video in one stream. It is not refused at extraction, since re-extracting one
  stream is legitimate; loading the streams together refuses it.

## Open problems and things not done

- **Locks after the retries.** `retry_while_locked` waits about 0.2 s in all, then raises. The frame cache logs that and goes on,
  but `FeatureStore.write` and `write_json_atomic` let it stop the extraction, and feature reads (`FeatureStore.load`) do not retry.
  This only matters if something else has the file open during the run; the retries were tested with mocks, not real processes.
- **A path row's file is compared by path only.** A file rewritten at the same path after extraction is not refused by
  `CachedFeatureDataset`, since the row check does not stat it.

- **Motion gain: open, for the coordinator to decide on real val clips.** The value is kept at 0.05 (+-1 at the clip).
  The reviewer's study (r3d_18, held-out 4-direction, synthetic, n=128: /20 0.805, /5 0.992, /1 1.000) is not grounds to
  pick a constant. Motion input is low in scale (std 0.028 vs rgb 0.90, V-042). `--motion_gain` is there to try values;
  each value needs its own folder.
- **Left for later (V-042):**
  - exact copies of a video at two paths are not caught by the split audit;
  - id-only manifests skip the trim check;
  - the probe uses last-epoch weights (T1's TrainingOptions, after merge);
  - standalone evaluate and embed do not inherit the resize;
  - torchcodec rotation is unverified (see below).

- **The accuracy cost of pooling (1x1 vs 2x2 vs 4x4) is not measured.** P-102 asks for storage and time, which are
  above; accuracy needs real data and pretrained weights. The attentive-probe test uses a constructed task, so it
  shows the mechanism works, not that it wins on real video.
- **Nothing here has run on the GPU, with pretrained weights, or on real video.** Coordinator command:
  `python scripts/bench_video_io.py --clips 200 --feature_clips 100 --feature_model r3d_18 --feature_pretrained --feature_gpu`.
  The determinism test is only run on CPU; exact equality on CUDA is unverified.
- **I did not run the full suite**, as instructed; only targeted tests.
- **Torchcodec is not installed here, so item 3 is verified with opencv only.** Its metadata reports rotation 0 like
  opencv, and the same code path handles it. Whether torchcodec's own frames come out in display orientation is
  unverified. If they do not, rgb on a rotated file is wrong with that backend, and this fix does not address it.
- Per-video predictions come only with `--test_df`; validation rows get none.
- Extraction decodes in the main process, one video at a time, with no DataLoader workers. Decoding may become
  the bottleneck on a GPU.
- A video's features are held in RAM until written. Vectors are fine; token grids on very long videos could be large.
- Two extractions writing to the same folder are safe per entry, but `features.json` is read-modify-write, so
  concurrent runs on different streams could lose a stream's registration until the next run re-registers it.
- `train_feature_head.py` does not fit the per-prediction error model and has no `infer.py` or GUI path; a trained
  probe can only be evaluated through `--test_df`. That is the rest of P-119. `build_video_model` was not extended.
- The frame cache has no size limit or eviction.
- `--num_workers` pickling of the cache is tested only through `pickle`, not a real spawned worker pool, to keep
  the test light on this machine.
- Windows behaviour with a concurrent reader and `os.replace` is exercised with threads, not separate processes.
- GUI widgets for these flags are not added (Phase 7); the Test page does pass the frame-cache flags.
